# Обработка ошибок

Architect Framework предоставляет мощную систему обработки ошибок и исключений, которая включает перехват PHP-ошибок, исключений, фатальных ошибок и отображение пользовательских страниц ошибок (404, 500 и др.). Система интегрирована с логированием и отладочной панелью, что позволяет эффективно диагностировать проблемы в разработке и обеспечивать безопасность в production.

## Введение

Система обработки ошибок Architect построена на сервисе `Errors`, который реализует интерфейсы `ErrorHandlerInterface` и `ErrorRendererInterface`. Ключевые возможности:

- **Перехват всех типов ошибок** – PHP errors, exceptions, fatal errors.
- **Пользовательские страницы ошибок** – 404 (Not Found), 500 (Internal Server Error), 403 (Forbidden) и другие.
- **Интеграция с логированием** – все ошибки автоматически логируются через PSR-3 логгер.
- **Режим отладки** – в development-окружении отображаются детальные stack traces, в production – безопасные сообщения.
- **Гибкая конфигурация** – настройка через конфигурационные файлы.

## Конфигурация

Конфигурация ошибок может быть определена в `app/config/errors.json` (если файл существует) или через другие конфигурационные файлы. Пример конфигурации:

```json
{
    "display_errors": true,
    "log_errors": true,
    "error_reporting": "E_ALL",
    "debug": true,
    "custom_pages": {
        "404": "errors/404",
        "500": "errors/500",
        "403": "errors/403"
    }
}
```

Настройки также могут быть унаследованы из конфигурации окружения (development, production).

## Типы ошибок

### PHP-ошибки

К ним относятся ошибки, генерируемые PHP: `E_ERROR`, `E_WARNING`, `E_NOTICE`, `E_DEPRECATED` и т.д. Обработчик ошибок перехватывает их через `set_error_handler` и преобразует в исключения или логирует.

### Исключения

Любые исключения (`Throwable`), не пойманные в коде приложения, перехватываются глобальным обработчиком исключений (`set_exception_handler`). Исключения логируются и отображаются как страница 500.

### Фатальные ошибки

Фатальные ошибки (например, `E_ERROR`, `E_PARSE`) не могут быть перехвачены стандартным обработчиком, но регистрируются в shutdown-функции. Система определяет, была ли фатальная ошибка, и отображает соответствующую страницу.

### Пользовательские ошибки

Вы можете вручную вызвать ошибку для определённых сценариев:

```php
$this->errors->display404('Запрашиваемая страница не найдена');
$this->errors->displayError('Внутренняя ошибка сервера', 500);
```

## Обработчики ошибок

### Инициализация

Сервис Errors автоматически инициализируется при загрузке приложения. Вы также можете инициализировать его вручную:

```php
$errors = $this->container->get('errors');
$errors->init();
```

Метод `init()` регистрирует обработчики ошибок, исключений и shutdown-функцию.

### Кастомизация обработчиков

Вы можете заменить стандартные обработчики, создав собственный класс, реализующий `ErrorHandlerInterface`, и зарегистрировав его в контейнере.

```php
<?php
namespace App\Errors;

use Architect\Services\Errors\Contracts\ErrorHandlerInterface;

class CustomErrorHandler implements ErrorHandlerInterface
{
    public function handleError(int $errno, string $errstr, string $errfile, int $errline): bool
    {
        // Кастомная логика обработки ошибки
        return true; // ошибка обработана
    }
    
    public function handleException(\Throwable $exception): void
    {
        // Кастомная логика обработки исключения
    }
    
    public function handleShutdown(): void
    {
        // Кастомная логика shutdown
    }
}
```

Зарегистрируйте в контейнере:

```php
$container->set('error_handler', new CustomErrorHandler());
```

## Отображение страниц ошибок

### Стандартные страницы

Architect предоставляет стандартные шаблоны для страниц ошибок:

- **404** – «Страница не найдена»
- **500** – «Внутренняя ошибка сервера»
- **Exception** – детальная информация об исключении (только в режиме отладки)

Шаблоны находятся в `architect/Services/Errors/View/` и используют простой HTML с возможностью стилизации.

### Кастомные страницы

Вы можете создать собственные шаблоны для страниц ошибок. Укажите пути в конфигурации:

```json
{
    "custom_pages": {
        "404": "errors/404",
        "500": "errors/500"
    }
}
```

Затем создайте файлы в `app/templates/errors/404.php` и `app/templates/errors/500.php` (или в Blueprint).

**Пример кастомной страницы 404:**

```php
<!DOCTYPE html>
<html>
<head>
    <title>404 - Страница не найдена</title>
    <style>
        body { font-family: sans-serif; text-align: center; padding: 50px; }
        h1 { color: #d9534f; }
    </style>
</head>
<body>
    <h1>404</h1>
    <p>Извините, запрашиваемая страница не существует.</p>
    <a href="/">Вернуться на главную</a>
</body>
</html>
```

### Режим отладки

В режиме отладки (когда `debug.enabled = true` и окружение не production) страницы ошибок содержат детальную информацию:

- Сообщение ошибки
- Файл и строка
- Stack trace
- Контекст запроса (если доступно)

В production-окружении отображаются только общие сообщения без деталей, чтобы избежать утечки информации.

**Включение/отключение отладки:**

```php
// В конфигурации debug.json
"enabled": true
```

## Логирование ошибок

Все ошибки автоматически логируются через PSR-3 логгер в канал `error`. Вы можете настроить уровень логирования и формат в `logger.json`.

**Пример записи в логе:**

```
[2026-03-13 23:45:12] error.ERROR: [Exception] Division by zero in /app/modules/calc/controller.php on line 42 {"category":"exception"}
```

**Категории ошибок:**

- `fatal` – фатальные ошибки
- `exception` – исключения
- `error` – PHP-ошибки уровня E_ERROR
- `warning` – предупреждения
- `notice` – уведомления
- `deprecated` – устаревшие функции

## HTTP-коды ответов

При отображении страницы ошибки автоматически устанавливается соответствующий HTTP-код ответа:

- **404** – `HTTP/1.1 404 Not Found`
- **500** – `HTTP/1.1 500 Internal Server Error`
- **403** – `HTTP/1.1 403 Forbidden`
- **401** – `HTTP/1.1 401 Unauthorized`

Вы можете указать код вручную:

```php
$this->errors->displayError('Доступ запрещён', 403);
```

## Интеграция с MVC

Обработка ошибок тесно интегрирована с MVC-архитектурой:

- **Контроллеры** – при возникновении исключения в контроллере оно перехватывается и отображается как страница ошибки.
- **Маршрутизация** – если маршрут не найден, автоматически вызывается страница 404.
- **Middleware** – middleware могут выбрасывать исключения, которые будут обработаны глобальным обработчиком.

**Пример обработки исключения в контроллере:**

```php
public function show($id)
{
    try {
        $user = User::findOrFail($id);
    } catch (ModelNotFoundException $e) {
        // Показать страницу 404
        $this->errors->display404('Пользователь не найден');
        return;
    }
    
    // ...
}
```

## Лучшие практики

1. **Всегда логируйте ошибки** – даже если вы отображаете пользовательскую страницу, ошибка должна быть записана в лог для последующего анализа.

2. **Не показывайте детали ошибок в production** – это может привести к утечке чувствительной информации (пути файлов, SQL-запросы и т.д.).

3. **Используйте кастомные страницы ошибок** – это улучшит пользовательский опыт.

4. **Настройте мониторинг ошибок** – отслеживайте частоту появления ошибок 500, 404 и других.

5. **Тестируйте обработку ошибок** – убедитесь, что в случае сбоя приложение ведёт себя предсказуемо.

6. **Используйте соответствующие HTTP-коды** – это важно для SEO и API-клиентов.

## Частые вопросы

**Вопрос: Как отключить обработку ошибок Architect и использовать собственную?**

Ответ: Не вызывайте `$errors->init()` или замените сервис `errors` в контейнере на свою реализацию.

**Вопрос: Как добавить отправку уведомлений об ошибках (например, в Slack или email)?**

Ответ: Создайте кастомный обработчик, который после логирования отправляет уведомление через нужный канал.

**Вопрос: Почему в production не отображается stack trace?**

Ответ: Это поведение по умолчанию для безопасности. Чтобы включить, установите `debug.enabled = true` и убедитесь, что окружение не production.

**Вопрос: Как изменить формат сообщений об ошибках в логах?**

Ответ: Настройте writer логгера (см. документацию по логированию) или создайте собственный.

**Вопрос: Можно ли использовать разные страницы ошибок для разных модулей?**

Ответ: Да, вы можете в обработчике проверить текущий модуль и отобразить соответствующую страницу.

**Вопрос: Как протестировать страницу 404 в development?**

Ответ: Перейдите по несуществующему URL, например, `/nonexistent`. Или вызовите в коде `$this->errors->display404()`.
