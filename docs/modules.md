# Модули

Модульная архитектура является одной из ключевых особенностей Architect Framework. Модули позволяют организовывать код в логические блоки, каждый из которых содержит контроллеры, модели, представления, конфигурации и другие ресурсы. Модули могут быть как глобальными (общими для всех приложений), так и принадлежать конкретному приложению.

## Введение

Модуль в Architect – это директория внутри `app/modules/` (для глобальных модулей) или `app/apps/{app}/modules/` (для модулей приложения), содержащая следующие поддиректории:

- `controller/` – контроллеры модуля
- `model/` – модели модуля
- `view/` – представления модуля
- `lang/` – файлы переводов (опционально)
- `config/` – конфигурации модуля (опционально)
- `assets/` – статические ресурсы (опционально)

Каждый модуль может иметь собственный файл `modulebootstrap.php`, который выполняется при инициализации модуля.

## Структура модуля

Пример структуры модуля `users`:

```
app/modules/users/
├── controller/
│   ├── UserController.php
│   └── ProfileController.php
├── model/
│   ├── User.php
│   └── Profile.php
├── view/
│   ├── user/
│   │   ├── index.php
│   │   └── show.php
│   └── profile/
│       ├── edit.php
│       └── show.php
├── lang/
│   └── en/
│       └── users.json
├── config/
│   └── settings.json
├── assets/
│   ├── css/
│   └── js/
└── modulebootstrap.php
```

**Минимальная структура** модуля может состоять только из контроллера и представления.

## Типы модулей

### Модули приложения

Модули приложения находятся внутри директории конкретного приложения: `app/apps/{app}/modules/`. Они доступны только для этого приложения и могут переопределять глобальные модули с тем же именем.

Пример: приложение `admin` может иметь модуль `dashboard`, который отличается от глобального модуля `dashboard`.

### Глобальные модули

Глобальные модули расположены в `app/modules/` и доступны всем приложениям. Они используются для общих функциональностей, таких как аутентификация, управление пользователями, блоги и т.д.

Если и глобальный, и модуль приложения имеют одинаковое имя, приоритет имеет модуль приложения (для текущего приложения).

## Создание модуля

### Вручную

1. Создайте директорию модуля в соответствующем месте:
   - Для глобального модуля: `app/modules/{module_name}/`
   - Для модуля приложения: `app/apps/{app}/modules/{module_name}/`

2. Создайте необходимые поддиректории (`controller`, `model`, `view` и т.д.).

3. Создайте базовые файлы (контроллер, представление).

### Через консольную команду

Architect предоставляет консольную команду для создания модуля:

```bash
bin/arc make:module users
```

Опции:
- `--app` – указать приложение (если модуль создаётся для конкретного приложения).
- `--global` – создать глобальный модуль (по умолчанию).
- `--controller` – создать контроллер вместе с модулем.
- `--model` – создать модель вместе с модулем.
- `--view` – создать представление вместе с модулем.

Пример создания модуля с контроллером и моделью:

```bash
bin/arc make:module products --controller --model
```

## Загрузка модулей

### Автоматическая загрузка

Модули загружаются автоматически при обращении к ним через маршрутизацию. Когда маршрут указывает на модуль `users` и контроллер `UserController`, система:

1. Определяет, является ли модуль глобальным или принадлежит приложению.
2. Ищет файл контроллера в соответствующей директории.
3. Загружает класс контроллера через автозагрузчик PSR-4.

### Bootstrap модуля

Если модуль содержит файл `modulebootstrap.php`, он выполняется при первой загрузке модуля. В этом файле можно зарегистрировать сервисы, добавить маршруты, выполнить миграции и т.д.

**Пример `modulebootstrap.php`:**

```php
<?php
// app/modules/users/modulebootstrap.php

use Architect\Core\Container;

// Получаем контейнер
$container = Container::getInstance();

// Регистрируем сервис модуля
$container->set('users.service', function() {
    return new \Modules\Users\Service\UserService();
});

// Добавляем маршруты модуля
$router = $container->get('router');
$router->addRoute('/users/profile', 'Users/ProfileController', 'index');

// Выполняем миграции (если нужно)
if (php_sapi_name() === 'cli') {
    // Миграции только для CLI
}
```

Bootstrap-файл выполняется один раз за запрос для каждого модуля.

## Разрешение путей и классов

### ModulePathResolver

Сервис `ModulePathResolver` отвечает за определение путей к файлам модуля. Он используется внутренними компонентами (загрузчиками контроллеров, моделей, представлений).

**Пример использования:**

```php
$resolver = $container->get('module_path_resolver');

// Получить путь к контроллеру
$path = $resolver->getControllerPath('users', 'UserController', false);

// Проверить, существует ли модуль
if ($resolver->moduleExists('users')) {
    // модуль существует
}
```

### ClassNameResolver

Сервис `ClassNameResolver` определяет полное имя класса (FQCN) для контроллеров, моделей и bootstrap-классов на основе соглашений об именовании.

**Соглашения об именовании:**

- **Глобальные модули:** `Modules\{Module}\Controller\{Controller}`
- **Модули приложения:** `Apps\{App}\Modules\{Module}\Controller\{Controller}`

Пример: для глобального модуля `users` и контроллера `UserController` класс будет `Modules\Users\Controller\UserController`.

**Использование:**

```php
$className = $resolver->buildControllerClassName('users', 'UserController', false);
// Возвращает: Modules\Users\Controller\UserController
```

## Маршрутизация и модули

Маршруты могут быть связаны с модулями через конфигурацию маршрутов (`app/routes/*.json`). Параметры `module` и `controller` определяют, какой модуль и контроллер будут обрабатывать запрос.

**Пример маршрута:**

```json
{
    "route": "/users",
    "module": "users",
    "controller": "UserController",
    "action": "index"
}
```

Если `module` не указан, используется модуль из пути (например, маршрут `/users/profile` может быть автоматически сопоставлен с модулем `users` и контроллером `ProfileController`).

**Автоматическое разрешение модуля:**

При включённой опции `app_routing` в `apps.json` маршрутизатор пытается автоматически определить модуль на основе сегментов URL. Например, URL `/users/profile` будет интерпретирован как модуль `users`, контроллер `ProfileController`, действие `index`.

## Взаимодействие между модулями

Модули могут взаимодействовать друг с другом через сервисы, события или прямые вызовы классов (если они загружены).

**Рекомендуемые способы:**

1. **Сервисы** – выносите общую логику в сервисы, регистрируйте их в контейнере и используйте в разных модулях.
2. **События (Event Dispatcher)** – используйте паттерн «Наблюдатель» для松散 связанного взаимодействия.
3. **API модуля** – создавайте публичные классы/интерфейсы, которые другие модули могут использовать.

**Пример использования сервиса из другого модуля:**

```php
// В модуле orders
$userService = $container->get('users.service');
$user = $userService->findUser($userId);
```

## Лучшие практики

1. **Соблюдайте принцип единственной ответственности** – каждый модуль должен отвечать за одну предметную область.

2. **Избегайте жёстких зависимостей между модулями** – используйте интерфейсы и внедрение зависимостей.

3. **Используйте глобальные модули для общей функциональности** – например, `auth`, `admin`, `api`.

4. **Документируйте публичный API модуля** – если модуль предназначен для использования другими разработчиками.

5. **Тестируйте модули независимо** – каждый модуль должен иметь свои unit-тесты.

6. **Следите за размером модуля** – если модуль становится слишком большим, рассмотрите возможность разделения на подмодули.

7. **Используйте конфигурации модуля** – храните настройки модуля в `config/` и загружайте их через `ConfigService`.

## Частые вопросы

**Вопрос: Можно ли иметь вложенные модули (подмодули)?**

Ответ: Прямой поддержки вложенных модулей нет. Вместо этого используйте точечную нотацию в имени модуля (например, `admin.users`) и создайте соответствующую структуру директорий `app/modules/admin/users/`. Однако автоматическое разрешение может не работать; потребуется настройка маршрутов вручную.

**Вопрос: Как переопределить глобальный модуль в приложении?**

Ответ: Создайте модуль с тем же именем в директории приложения. При обращении к модулю из этого приложения будет использоваться локальная версия.

**Вопрос: Как получить список всех модулей (глобальных и приложения)?**

Ответ: Используйте сервис `ModulePathResolver` или просканируйте директории `app/modules/` и `app/apps/*/modules/`.

**Вопрос: Можно ли отключить модуль без удаления?**

Ответ: Да, удалите или переименуйте файл `modulebootstrap.php`, либо исключите модуль из маршрутов. Также можно добавить флаг в конфигурацию модуля и проверять его при загрузке.

**Вопрос: Как поделиться ресурсами (CSS, JS) между модулями?**

Ответ: Разместите общие ресурсы в глобальном модуле (например, `common`) и используйте хелпер `Assets` для включения в шаблоны.

**Вопрос: Как создать модуль, который будет доступен только через API?**

Ответ: Создайте модуль без представлений (`view/`), только с контроллерами, возвращающими JSON. Настройте маршруты с префиксом `/api/`.
