# Отладка и отладочная панель

Architect Framework включает мощную интерактивную отладочную панель, которая предоставляет детальную информацию о выполнении приложения: время выполнения, использование памяти, SQL-запросы, кэширование, сессии, маршрутизацию и многое другое. Панель отображается в нижней части экрана в режиме разработки и помогает быстро выявлять проблемы.

## Введение

Отладочная панель Architect (Debug Panel) — это инструмент, который автоматически собирает метрики выполнения приложения и отображает их в удобном интерфейсе. Панель доступна только в режимах разработки и тестирования (не в production) и может быть ограничена по IP-адресам.

Основные возможности:

- **Мониторинг производительности** – время выполнения, использование памяти, пиковое потребление.
- **Анализ SQL-запросов** – список всех выполненных запросов, их длительность, параметры.
- **Кэширование** – статистика попаданий/промахов кэша, операции с кэшем.
- **Сессии и куки** – просмотр данных сессии и cookies.
- **Маршрутизация** – информация о текущем маршруте, параметрах, загруженных файлах маршрутов.
- **Логирование** – сообщения, предупреждения, ошибки, сгруппированные по категориям.
- **Интеграция с Blueprint** – данные о компиляции шаблонов, ошибках шаблонизатора.
- **Кастомные данные** – возможность добавлять свои секции через сборщики данных.

## Конфигурация

### Файл debug.json

Настройки отладки хранятся в `app/config/debug.json`:

```json
{
    "enabled": true,
    "log_to_file": true,
    "log_categories": ["info", "warning", "error"],
    "show_queries": true,
    "show_memory": true,
    "show_time": true,
    "show_includes": true,
    "show_session": true,
    "show_cookies": true,
    "collect_custom_data": true,
    "ip_whitelist": [],
    "max_messages": 1000,
    "max_data_size": 1048576,
    "auto_refresh": false,
    "auto_refresh_interval": 2000
}
```

**Опции:**

- `enabled` – включить/выключить отладочную панель.
- `log_to_file` – дублировать логи в файл (app/logs/debug_*.log).
- `log_categories` – категории логов, которые записываются в файл.
- `show_*` – отображать соответствующие секции в панели.
- `collect_custom_data` – разрешить сбор кастомных данных через DebugCollector.
- `ip_whitelist` – массив IP-адресов, для которых панель будет отображаться (пустой массив – все адреса).
- `max_messages` – максимальное количество сообщений в памяти (во избежание утечек).
- `max_data_size` – максимальный размер данных в байтах.
- `auto_refresh` – автоматическое обновление панели (например, для мониторинга AJAX-запросов).
- `auto_refresh_interval` – интервал автообновления в миллисекундах.

### Включение/отключение

Панель автоматически отключается в production-окружении (определяется через `environment`). Вы можете принудительно включить или отключить её в коде:

```php
$debug = $this->container->get('debug');
if ($debug->isEnabled()) {
    // панель активна
}
```

### Белый список IP

Если нужно ограничить доступ к отладочной панели только для определённых IP-адресов, укажите их в `ip_whitelist`:

```json
"ip_whitelist": ["192.168.1.100", "127.0.0.1"]
```

## Отладочная панель

### Секции панели

Панель состоит из нескольких секций (виджетов), которые можно сворачивать/разворачивать:

1. **Performance** – общее время выполнения, время по стадиям, использование памяти, лимит памяти.
2. **Database** – список SQL-запросов с длительностью, параметрами, подсветкой медленных запросов (>100 мс).
3. **Logs** – сообщения, залогированные через `$debug->log()`.
4. **Cache** – статистика кэширования: попадания, промахи, соотношение, операции.
5. **Session** – данные сессии (если включено).
6. **Routing** – текущий маршрут, параметры, загруженные файлы маршрутов.
7. **Environment** – текущее окружение (development, testing, staging, production).
8. **Blueprint** – информация о компиляции шаблонов Blueprint, ошибках, путях загрузки.
9. **Custom Data** – кастомные данные, добавленные через DebugCollector.

### Виджеты

Каждая секция представлена в виде виджета с цветовой индикацией:

- **Зелёный** – нормальные значения (быстрые запросы, низкое использование памяти, высокий hit-ratio кэша).
- **Жёлтый** – предупреждение (средние значения).
- **Красный** – критические значения (медленные запросы, высокое использование памяти, низкий hit-ratio кэша).

## Использование сервиса Debug

### Логирование

Вы можете добавлять собственные сообщения в отладочную панель:

```php
$debug = $this->container->get('debug');

// Простое сообщение
$debug->log('Пользователь залогинен', 'info');

// С контекстом
$debug->log('Ошибка валидации', 'error', [
    'field' => 'email',
    'value' => 'invalid@example',
]);

// Категории: info, warning, error, debug, query, cache, etc.
```

Сообщения отображаются в секции **Logs** и, если включено `log_to_file`, записываются в `app/logs/debug_YYYY-MM-DD.log`.

### Замеры времени

Вы можете измерять время выполнения отдельных этапов (стадий) приложения:

```php
$debug->startStage('database_queries');
// ... выполнение запросов ...
$debug->endStage();
```

Стадии отображаются в секции **Performance** с детализацией по времени.

### Отслеживание SQL-запросов

Axiom ORM автоматически передаёт запросы в отладочную панель. Вы также можете вручную добавить запрос:

```php
$debug->query('SELECT * FROM users WHERE id = ?', 0.045, [42]);
```

Параметры:
- SQL-запрос
- Длительность в секундах
- Массив параметров (опционально)

Запросы, длительность которых превышает 100 мс, помечаются как медленные и выделяются красным.

### Кэширование

Сервис кэширования автоматически сообщает о попаданиях и промахах. Вы можете вручную добавить информацию:

```php
$debug->cacheHit('user_profile_42');   // попадание в кэш
$debug->cacheMiss('user_profile_42');  // промах
$debug->cacheSet('user_profile_42');   // запись в кэш
```

Статистика отображается в секции **Cache**.

### Данные сессии

По умолчанию панель показывает данные сессии, если включена опция `show_session`. Вы можете обновить данные вручную:

```php
$debug->setSessionData($_SESSION);
```

## Интеграция с Blueprint

Отладочная панель собирает информацию о работе шаблонизатора Blueprint:

- **Компиляция шаблонов** – какие шаблоны были скомпилированы, использовался ли кэш.
- **Ошибки компиляции** – сообщения об ошибках, фрагменты скомпилированного кода.
- **Пути загрузки** – список путей, по которым ищутся шаблоны.

Данные автоматически добавляются при использовании Blueprint. Вы можете вручную добавить информацию:

```php
$debug->blueprintCompile('user/profile', '/path/compiled.php', false);
$debug->blueprintError('user/profile', 'Syntax error in template', $code);
```

## Кастомные сборщики данных

Вы можете расширить отладочную панель своими данными, создав класс, реализующий `DebugCollectorInterface`:

```php
<?php
namespace App\Debug;

use Architect\Services\Debug\Contracts\DebugCollectorInterface;

class CustomCollector implements DebugCollectorInterface
{
    private array $data = [];
    
    public function collect(): void
    {
        $this->data['custom'] = [
            'timestamp' => time(),
            'user_agent' => $_SERVER['HTTP_USER_AGENT'] ?? '',
            'custom_metric' => 123,
        ];
    }
    
    public function getData(): array
    {
        return [
            'has_data' => !empty($this->data),
            'data' => $this->data,
        ];
    }
    
    public function clear(): void
    {
        $this->data = [];
    }
}
```

Зарегистрируйте сборщик в контейнере или подключите через конфигурацию.

## Консольные команды для отладки

Architect предоставляет консольные команды, полезные для отладки:

```bash
# Показать информацию о системе
bin/arc info

# Очистить кэш
bin/arc cache:clear

# Показать список маршрутов
bin/arc route:list

# Запустить тесты
bin/arc test:run
```

## Лучшие практики

1. **Не включайте отладочную панель в production** – это может привести к утечке чувствительной информации и снижению производительности.

2. **Используйте IP-белый список** для ограничения доступа к панели в staging-окружении.

3. **Логируйте контекст** – при логировании ошибок добавляйте как можно больше контекстной информации (ID пользователя, параметры запроса и т.д.).

4. **Отслеживайте медленные запросы** – настройте оповещения о запросах длительностью >100 мс.

5. **Мониторьте hit-ratio кэша** – низкий показатель (<40%) может указывать на неэффективное использование кэша.

6. **Используйте стадии (stages)** для профилирования сложных операций.

7. **Очищайте данные отладки** между запросами в долгоживущих процессах (например, воркеры очередей) во избежание утечек памяти.

## Частые вопросы

**Вопрос: Как полностью отключить отладочную панель?**

Ответ: Установите `"enabled": false` в `debug.json` или переключите окружение на production.

**Вопрос: Панель не отображается, хотя enabled=true. В чём причина?**

Ответ: Проверьте:
- Окружение (в production панель автоматически отключается).
- IP-белый список (если ваш IP не в списке, панель не покажется).
- Наличие вывода `$debug->render()` в шаблоне (обычно это делается автоматически).

**Вопрос: Как добавить свою секцию в панель?**

Ответ: Создайте кастомный сборщик данных (реализуйте `DebugCollectorInterface`) и зарегистрируйте его в контейнере. Данные появятся в секции **Custom Data**.

**Вопрос: Можно ли использовать отладочную панель в API-запросах (JSON)?**

Ответ: Да, но панель рендерится как HTML. Для API лучше использовать логирование в файл или отдельный endpoint для метрик.

**Вопрос: Как просмотреть логи отладки в файле?**

Ответ: Логи хранятся в `app/logs/debug_YYYY-MM-DD.log`. Вы можете использовать команду `tail -f` или открыть файл в редакторе.

**Вопрос: Влияет ли отладочная панель на производительность?**

Ответ: Да, сбор данных добавляет небольшие накладные расходы. В production рекомендуется полностью отключать отладку.
